# `issue` — выписка полисов через NDP API

Реализовано на ветке `feat/policy-issuance`. Этот файл — отдельно от общего
`README.md` (который живёт на другой ветке и ещё не смёржен), чтобы не
плодить конфликт при объединении веток: сюда вынесено только то, что
добавлено в рамках этой фичи.

## Что делает

Команда бота `issue <продукт>` выписывает страховой полис: пользователь
присылает JSON тела запроса на следующих строках сообщения, бот пробрасывает
его как есть в POST к NDP API и возвращает идентификаторы запущенного
процесса выписки.

```
issue ns
{
  "city": "Almaty",
  "contract_type": "adult",
  ...
}
```

Без JSON (просто `issue ns`) бот присылает пример payload'а для этого
продукта. Если продукт не распознан — показывает список поддерживаемых и
примеры по каждому.

## Поддерживаемые продукты

| Ключ команды | Эндпоинт NDP | Особенность payload'а |
|---|---|---|
| `ns` | `POST /v1/ui/policy/v1/ns/policies` | несчастный случай; `insureds[]` + `policyholder` |
| `mst` | `POST /v1/ui/policy/v1/mst/policies` | мед. страхование туристов, `variant: "standard"` |
| `mst-premium` | `POST /v1/ui/policy/v1/mst/policies?variant=premium` | тот же эндпоинт MST, но с query-параметром `variant=premium` |
| `ogpo-vts` | `POST /v1/ui/policy/v1/ogpo-vts/policies` | автогражданка; совсем другая структура — `drivers[]`, `vehicle`, `quote_id` вместо `insureds`/`policyholder` |

Все четыре варианта проверены живыми запросами к `api-dev.myndp.kz`.

## Как это устроено технически

- **Парсинг команды.** `bot.js` передаёт в `handleIssue` не разбитый по
  пробелам массив аргументов (как для других команд), а весь исходный текст
  сообщения целиком — иначе JSON с переносами строк и пробелами внутри был
  бы разорван. Внутри `issueHandler.js` продукт и JSON достаются регуляркой
  `/^issue\s+(\S+)\s*([\s\S]*)$/i`.
- **Payload — сквозной проброс.** Бот не валидирует и не дополняет тело
  запроса — что пользователь пришлёт, то и уходит в API. Ошибки валидации
  возвращает сам NDP.
- **Авторизация (`src/ndp/client.js`).** `login()` делает
  `POST /v1/ui/iam/v1/auth/staff/login` с `MYNDP_LOGIN`/`MYNDP_PASSWORD`,
  токен кэшируется в памяти процесса, срок жизни берётся из `exp` внутри
  самого JWT. При 401 от API кэш сбрасывается и логин повторяется один раз.
- **Ответ асинхронный.** Эндпоинты выписки не возвращают готовый договор —
  они стартуют BPM-процесс и отдают только `business_key` и
  `process_instance_id`. Сам полис (с номером договора, статусом
  `completed`) появляется в системе чуть позже — это подтверждено прямыми
  запросами к `GET /contracts` во время разработки.

## Находки по API (важны для дальнейшей работы)

- Заголовок `X-CURRENT-USER-ID`, помеченный в Swagger как обязательный, на
  практике не проверяется — сервер сам достаёт `user_id` из payload JWT
  (`{"user_id": "...", "staff_id": ...}`).
- Enum `contract_type` (`adult`/`children`) нигде не задокументирован и не
  отдаётся через API как справочник (`GET /v1/ui/policy/v1/ns/schema`
  отдаёт словари для формы — суммы, возраст, зоны и т.д., но не
  `contract_type`). Значения получены провокацией 422-ошибки валидации.
- Значит для остальных "селекторных" полей в payload'ах (`age_experience_id`,
  `driver_license_type_id`, `country_id`, `tariff` и т.п.) готового
  источника допустимых значений тоже может не быть — придётся либо искать
  похожие `/schema`-эндпоинты по каждому продукту, либо так же провоцировать
  ошибки валидации.

## Известные ограничения

- Тестовые личности/машины (IIN, `esbd_client_id`, паспортные данные,
  `vehicle_esbd_id` и т.д.) — захардкожены в примерах и должны существовать
  как реальные записи в dev ESBD; случайно сгенерировать их нельзя. Для
  расширения набора тестовых данных нужен отдельный список от тимлида
  (обсуждалось отдельно, ещё не реализовано).
- На этой ветке нет команды для проверки результата выписки (просмотр
  списка/деталей полиса) — та функциональность (`listContracts`,
  `getContractByNumber`) реализована на ветке `feat/policy-retrieval` и пока
  не смёржена.
- `contract_type` для `ns` жёстко ограничен двумя известными значениями —
  рандомизация этого поля рассматривалась, но по решению пользователя не
  включена (payload идёт как прислали).
